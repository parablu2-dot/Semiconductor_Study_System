"자연어 요구 문장을 구조화된 spec.json으로 바꾸는" 첫 단계. 페르소나·운영 틀을 먼저 잡고, spec-interpreter를 로컬 Claude CLI 호출로 자동화한 뒤, 새 모듈마다 사람이 먼저 설계를 굳히고 그 설계를 거꾸로 자연어 템플릿으로 표현하는 절차를 반복했다.

## 페르소나·거버넌스 설계
프로젝트 운영에 쓸 페르소나 구조와 주간 리뷰 템플릿을 가장 먼저 설계했다 — 이후 모든 자동화 세션이 이 틀 위에서 진행된다.

### S2 페르소나 설계 + Weekly Review 템플릿 (재구성)
프로젝트 운영에 쓸 페르소나 구조와 주간 리뷰 템플릿을 설계했다.  
**원문**: Dave (커밋 미태깅 세션 — README/프로젝트 기록 기준)

## spec-interpreter 자동화
'자연어 요구 문장 → spec.json' 해석을 사람 손이 아니라 로컬 `claude` CLI 서브프로세스 호출로 자동화했다. API 키 없이 이미 인증된 CLI를 그대로 재사용하는 것이 1인기업 PoC에 맞는 선택이었다.

### S6 spec-interpreter 자동화
'요구 문장 → spec.json' 해석을 로컬 claude CLI 서브프로세스 호출로 자동화했다(API 키 불필요).  
**원문**: Dave @e51a631

## 자연어 요구사항 템플릿
새 모듈을 만들 때마다 먼저 사람이 레지스터 맵을 손으로 설계해 'spec.json→RTL' 자동화만 검증하고, 그 설계를 거꾸로 자연어 문장으로 표현하는 템플릿은 한 라운드 뒤에 따로 만드는 2단계 절차가 UART/SPI부터 FIFO·인터럽트·SPI 슬레이브·cdc_sync까지 반복됐다. 절차 신뢰도가 쌓인 뒤에는(PWM부터) 두 단계를 한 라운드에 합쳤다.

### S11 UART/SPI 자연어 요구사항 템플릿
S10에서 손으로 쓴 spec.json을 거꾸로 자연어 문장으로 표현하는 템플릿을 만들어 spec-interpreter 단계까지 포함한 전체 체인을 검증했다.  
**원문**: Dave (커밋 미태깅 세션 — README/프로젝트 기록 기준)
