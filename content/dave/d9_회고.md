## 완주 소감
114개 세션에 걸쳐 "자연어 요구 → spec.json → RTL → cocotb/Yosys 검증"이라는 폐루프 한 바퀴(S6~S8)가 15개 모듈 생성(d2)과 SoC 통합(d2), 두 갈래 검증(cocotb + 형식 등가검사, d3), 두 트랙(FPGA 실물/d4, ASIC PnR·Sign-off/d5), 그리고 App 7종(d6)까지 확장됐다. 가장 반복된 경험은 "처음 세운 가설이 다음 세션에서 정정되는" 패턴이었다 — ss 코너 타이밍 병목의 진짜 원인(S59→S66→S67), PnR 다이 면적이 RTL 개선 효과를 가리는 현상(S69~S82), 실물 보드의 "파란 LED 고정"이 부팅 실패가 아니라 핀 배정 문제였던 것(S94)까지, 매번 실측으로 이전 결론을 검증하거나 뒤집는 과정이 이 프로젝트의 실제 작업 방식이었다.

## 반복된 디버깅 패턴
- **환경/배선을 논리 버그로 오인**: S94(RGB LED 파란 고정 → 전용 패드 배선 문제), S105(LED 버그 재발 → build_bitstream.sh 문제), S108(UART 벌크 전송 깨짐 → PC측 페이싱 문제).
- **Windows 서브프로세스·PATH 환경 버그의 반복 재발**: S46(subprocess orphan)과 같은 종류의 PATH 함정이 S52·S85·S86에서 형태를 바꿔 재발했다 — 한 번 고친 환경 버그도 완전히 영구화되지 않으면 다시 걸린다.
- **자동화 훅이 조용히 실패**: S47에서 만든 용어집 자동 갱신 훅이 S48~S59 내내 실행되지 않았고(S60), 그 수정 자체도 사각지대가 남아 있었다(S61) — 자동화는 도입 직후 end-to-end로 실행 여부를 직접 확인해야 한다.
- **이전 세션 진단을 다음 세션이 실측으로 정정**: S59→S66→S67(ss 코너 병목 원인), S64→S65(PnR 변동성 vs 결정론적 부수효과) — "정직하게 보고하고 다음 세션에서 검증"하는 순환이 이 프로젝트 전체를 관통한다.

## 남은 한계
1. **ss 코너 타이밍이 목표에 못 미쳤다** — 여러 라운드의 RTL 개선(카운터 제거, 파이프라이닝, PC 경로 리타이밍)과 DIE_AREA 스윕을 거쳐 fmax 약 79MHz까지 끌어올렸지만, 목표였던 100MHz에는 도달하지 못했다. PC/ALU 구조적 병목은 PicoRV32 코어 자체의 전면 재설계 없이는 더 줄이기 어렵다는 결론으로 PPA 최적화를 별도 프로젝트로 이월했다(S83).
2. **i2c_slave_burst 재현율이 약 13%~60% 구간을 오갔다** — 가장 복잡한 다상태 리액티브 FSM의 자연어→RTL 자동 생성은 근본적으로 확률적이며, baseline 조건(PATH 수정+timeout 1200s)을 확정한 뒤에도 완전한 결정성에는 도달하지 못했다(S91 최종 60%).
3. **Windows 환경 잡음** — subprocess orphan, PATH shadow, eqy 파티션 스택 오버플로처럼 이 프로젝트의 적지 않은 세션이 RTL 로직이 아니라 Windows 네이티브 환경의 한계(WSL 이전으로 우회) 때문에 소모됐다.
