# CUDA/GPU 프로그래밍 모델

## 1. 현재 표준 — 축적의 산물

CUDA(2007 발표)는 SIMT(Single Instruction, Multiple Thread) 모델을 중심으로 시스템·SW 계층의 왕좌에 올랐다. 이 승리는 단일 원인이 아니라 축적의 산물이다 — SIMT 모델이 하드웨어 스레드 관리를 단순화해 커널 작성 문턱을 낮췄고, cuDNN·cuBLAS·cuSPARSE·NCCL·CUTLASS 같은 도메인 특화 라이브러리가 세대별로 하드웨어에 맞춰 다시 튜닝돼 애플리케이션 개발자가 손대지 않아도 성능이 따라 올라갔으며, ABI·PTX의 세대 간 호환이 코드 자산의 반감기를 늘렸다.

## 2. 한계 — 경쟁 표준들이 각자 다른 이유로 진 자리

**OpenCL**은 표준화 정치와 벤더별 구현 편차로 "이론상 이식성 있지만 실측 성능은 벤더별 완전 재작성"이라는 함정에 빠졌다. **OpenMP offload**는 컴파일러 성숙과 실측 성능 격차로 HPC 외부에서 자리를 못 잡았다. **AMD ROCm/HIP**는 후발이면서 세대 간 지원 편차(특정 GPU만 지원)로 신뢰를 쌓지 못했고, 최근 MI300 세대에서 재도전 중이지만 여전히 CUDA 대비 라이브러리 성숙도가 낮다. **Intel oneAPI/SYCL**은 표준으로서의 완성도는 높지만 최상위 하드웨어 시장 점유 부재로 개발자 인력이 몰리지 않았다.

이 한계들의 공통점은 기술적 열세가 아니라 **생태계 잠금**이다 — [[euv-lithography]]에서 EUV가 대안들을 이긴 것과 같은 계열의 승리 메커니즘이 여기서도 반복된다.

## 3. 대안 후보

**Triton(OpenAI, 2019~).** Python DSL로 CUDA C++ 없이 GPU 커널을 쓸 수 있게 하고, torch.compile의 백엔드로 채택되면서 사용 빈도가 급증했다. 미해결은 최상위 성능이 여전히 수작업 튜닝된 CUDA C++ 커널(FlashAttention·CUTLASS 등)에 미치지 못하고, NVIDIA 외 백엔드에서의 성숙도 편차가 크다는 것이다. Triton이 "CUDA를 대체하는 문법"이 될지 "CUDA 위의 편의 계층"에 머무를지는 논쟁 중이다.

**SYCL·oneAPI.** 벤더 중립 프로그래밍 모델의 재도전으로, 표준으로서의 완성도는 높고 인텔 GPU·CPU에서 실측 성능도 검증되고 있다. 미해결은 NVIDIA·AMD GPU에서의 실측 성능 격차와 개발자 인력의 관성이다 — "표준으로서는 옳지만 시장이 채택하지 않는다"는 OpenCL의 반복이 될 가능성이 논쟁 지점이다.

**MLIR 계열 컴파일러(XLA·IREE·Mojo).** 프론트엔드와 백엔드 사이에 공통 IR을 두어 벤더 파편화를 흡수하려는 접근으로, [[pytorch-jax-framework]]와 접점을 이룬다.

## 4. 상위(되돌아가는) 영향 — 아래 계층에 요구하는 것

CUDA 지배가 유지되는 한, 이 계층은 다른 벤더들에게 **"CUDA 호환 레이어 유지 비용"**을 지속적으로 강제한다 — AMD·Intel의 프로그래밍 모델이 독자 생태계를 구축하지 못하는 한, CUDA 코드를 재컴파일·재작성 없이 돌리려는 호환 레이어(HIP의 CUDA 소스 변환 등) 유지가 이들 벤더의 소프트웨어 투자를 계속 흡수한다.

**회로·IP 계층에 SerDes·저전력 인터커넥트 IP의 벤더 종속을 강화한다** — NCCL이 NVLink·NVSwitch 토폴로지에 최적화돼 있어, 이 계층의 소프트웨어 표준이 하드웨어 인터커넥트 설계([[chiplet-ucie]] 관련 D2D 표준 포함)의 사실상 벤치마크가 된다.

**아키텍처 계층에 "CUDA 친화적 마이크로아키텍처"로의 수렴 압력을 강제한다** — [[von-neumann-cache-hierarchy]]에서 다룬 명시적 스코프 병렬 모델(CUDA·SYCL·HSA류)의 확산이, 새 가속기 설계가 처음부터 CUDA 프로그래밍 모델과의 호환을 전제로 시작하게 만드는 관성으로 작동한다.
